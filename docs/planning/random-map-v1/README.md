# 可控节点数量的随机地图：接入研究 v1

> 最新进展：M1/M2已实现，见[实施记录](implementation.md)与审核目录。下文保留最初研究提案，未实现事项以实施记录为准。

日期：2026-11-04。状态：代码与资源调研、设计提案；尚未实现生成器、设置界面或运行接入。本轮不修改正式玩法、人物美术或现有存档，不打包IPA。

## 1. 结论与来源

采用“先生成节点与道路，再用现有林地资源布景”。各类节点按配置精确分配，位置、道路与具体内容随机。节点数量、拓扑与场景布景应分开保存，规则层与画面共用节点ID和道路关系。

原桌游需求已有相同约定：指定总节点数，系统建议各类数量，教师可修改；开局前可重生成，开局后可换单节点怪物/奖励。默认10节点：起点1、战斗4、Boss1、奖励3、空地点1；首版界面预设4—30。起点固定1，其余非负整数，总和必须等于总节点数，Boss允许0。规则来源是本机只读快照 `boardgame-audit/main/docs/课堂桌游_需求设计_v1.md` §5.1—5.4、`课堂桌游_开发步骤_v1.md` 阶段4；不是对上游最新提交的查询。vendored规则来源提交见 `Vendor/ClassroomGameCore/UPSTREAM.json`。

自动建议沿原需求：战斗=floor(0.4N)，奖励=floor(0.3N)，Boss=1，起点=1，剩余为空地点。建议只在用户主动点击“采用建议”时替换已手改数量。

## 3. 配置与精确配额

示例见 [configuration-example.json](configuration-example.json)，仅为提案输入，不是App现有可读配置。

| 参数 | 首版行为 |
| --- | --- |
| 总节点数 | 默认10，界面预设4—30；这是首版范围，不当成永远不可扩展的规则限制 |
| 起点、战斗、Boss、奖励、空地点 | 起点固定1，其余可分别输入或加减，必须精确满足配额 |
| 数量校验 | 拒绝负数/小数；显示已分配/剩余/超出数量；总和不符不生成，不静默裁剪或补战斗节点 |
| 随机种子 | 可输入/复制；同生成器版本、配置和种子产生同样结果 |
| 分叉/环路 | 道路选项，与各类节点数量分开；首版可设少/中/多，底层转换为明确约束 |
| Boss距离 | 按距离起点的最短道路数筛选较远节点，不以屏幕欧氏距离判断；Boss=0时不应用 |
| 节点内容 | 战斗节点数量不等于怪物只数；怪物组合和奖励内容单独选择，读现有目录和原规则 |

推荐界面：一张“地图设置”面板，包含总数、五类数量、道路复杂度、种子，下方显示配额统计与随机预览；提供“采用建议”“换个种子预览”“确认开局”。生成过程中不写当前游戏档案。开局前才能整图重生成；开局后编辑单节点不改变整图结构，不把已领过的奖励恢复为可领取。

首版不引入商店/治疗/营地等新NodeKind；起点可显示营地。此类地点以后若要产生新规则，需要明确扩展，不能只加图标就宣称支持。

## 4. 生成顺序

1. 校验数量、道路约束与地图容量；保存规范化配置。数量与空间约束冲突时返回具体原因，不减少节点或偷偷改配额。
2. 生成有间隔的节点位置。设置独立布局区域、节点停留区和建筑占地；节点增多时优先扩展布局/平移缩放镜头，不把人物与建筑缩小到看不清。
3. 在无穿越节点的候选连线上建立连通树，再加入配置允许的环路。无自环、重复边、孤岛；分叉度约束需在构造时保证。连通图环路数为E−N+1，可用于核对结果。
4. 固定起点，按最终图的最短道路数挑选Boss候选；不足以满足约束就有限重试/明确失败。其余类型从精确数量的类型列表随机分配，不能逐节点按概率抽取后期望数量凑巧正确。
5. 给节点安排实际怪物/奖励。起点没有敌人；组合读取现有目录，不自动修改怪物属性。奖励完成状态从新局初始值开始；继续存档则直接读取已保存值。
6. 把每条图边转换为带宽度和控制点的道路。检查最终平滑曲线，而不只检查端点直线：不能穿过无关节点、制造没有逻辑路口的道路交叉、形成步态易抖动的尖锐短折线。
7. 按节点类型组装空地/营地/石树小景，保留人物与标记的可读区域。树石与建筑避开道路通行带、停留区和彼此占地，再填充路边草花。装饰使用独立随机流，改花草密度不改变节点、道路、怪物或战斗骰值。
8. 验证GameMap、配额、布局与资源引用；输出生成快照。完整场景重建在加载阶段完成，不在每帧重新生成。

拓扑、布局、内容、装饰使用固定算法/版本的独立seed子流和稳定排序；不使用Swift随机Hash值派生种子。重试次数有上限，失败保留输入与原因。

## 5. 规则与画面必须共用道路

当前TrailNetwork按道路几何长度挑最短路；规则GameMap按经过道路条数计距离和AP。两者不总是一致。正式移动先由GameEngine.preview(.move)选定并验证节点路径，再把同一条路径逐边展开为行走曲线，不能让渲染器另选一条“更短”的几何路。道路曲线再长仍按原规则每边1AP，不按像素距离收费。

预检失败不开始动画、不扣AP。有效行动只结算一次；遇到首个敌人节点沿规则结果停止，并按真实经过道路数扣点。玩家可见位置、揭示、奖励与遇敌展示需按到达时刻协调，不能在动画起点提前展示终点奖励/隐藏敌人。取消、暂停或切后台也不能重复结算。实现阶段需明确已提交回执与移动播放游标的恢复方式。

正式节点战斗应由同一个行程GameEngine驱动，复用当前近身/远程动作、技能、UI和地图背景；不能把抵达敌人简单接到会重置HP/补给的独立演练场。此处是第二阶段集成工作，生成地图本身不等于已完成正式探索与战斗。

## 6. 布局、性能与保存

- 首轮可先在现有林地范围验证默认10节点。4—30节点完整支持需要把固定bounds、镜头中心、出生点、营地避让区和发现点数量假设改为布局数据；高数量地图保持角色原比例，允许镜头平移/缩放。
- 道路遮罩与地图阴影尺寸受世界范围影响；不能只扩大世界坐标，遗漏Metal/SpriteKit遮罩、相机与资源预算。使用共享纹理，物件数量和投影数量设置预算；需要扩大地图时评估分块遮罩和可视区域裁剪。
- 保持60fps为运行目标；生成和资源准备放到加载阶段。实际设备FPS、耗电、峰值内存仍由设备测试确认，研究不声称已达标。
- 保存实际GameMap、节点事件/奖励领取/揭示状态、单位与战斗档案、完整布局/道路控制点/props、配置、seed和generatorVersion。继续游戏加载实际快照，不能只凭seed再生成。
- 新建探索存档封装，与原camp-v1.json分开演进；不要把营地装配档直接改成半兼容的战役档。GameArchive原规则格式保持，新增布局数据由本地封装承载。原子保存成功再提交新局，失败保留旧档。
- 单节点怪物/奖励编辑要作为可追溯操作设计；现有GameMap字段可承载结果，不等于已有完整编辑命令。修改奖励内容不能重置rewardCompleted，重置事件需独立明确操作。

## 7. 实施顺序与验收

| 顺序 | 可交付内容 | 核查重点 |
| --- | --- | --- |
| M1 纯生成器 | 独立Foundation模块、配置校验、GameMap+布局输出、固定种子离线预览 | 配额精确、连通、重复边/自环、起点无敌、Boss约束、确定性、失败边界；先不改变现有演示入口 |
| M2 设置与林地预览 | 原生节点数量控制、种子输入、地图预览；复用现有地表/道路/树石/营地/阴影 | 多个种子/4、10、30节点全图与近景；不挡路、不漂浮、不产生假路口，后台资源准备和帧预算 |
| M3 正式探索会话 | 同一规则引擎的路径预检/实际节点移动、共享揭示、奖励与敌人触发、存档续行程 | AP按道路数、遇敌停步、同次多人奖励、稍后到达不重复奖励、重入/恢复不二次结算；沿用战斗动作和布局 |
| M4 节点内容编辑 | 单节点替换怪物/奖励、历史与明确的事件重置 | 已领取不自动重发；整图重生成仅新局准备阶段 |

M1建议覆盖4—30每个N和多种seed，另测Boss=0、无战斗、全空地点、配额不符、空间/道路约束矛盾、最大数量；检查同输入逐字节一致、只改装饰不影响玩法、失败有上限。M2才做现有实际资源的全场静态与正常速度行走GIF审查；不得用抽象图示冒称游戏画面。M3复用原移动预检、奖励/战斗测试并补完整会话测试。

本轮只完成研究和示例配置的静态核对；上述生成、性能、交互与测试均为后续待做项。推荐下一项M1，随后M2；M3是把地图从“可看可走”推进到正式玩法的必要阶段。
